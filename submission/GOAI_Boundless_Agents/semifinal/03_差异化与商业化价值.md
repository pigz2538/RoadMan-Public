# 优化方向三：突出差异化与商业化价值

## 1. 目标用户不是“所有旅行者”

RoadMan 首先服务三类高约束用户：

| 用户 | 真实任务 | 现有通用工具中的断点 |
|---|---|---|
| 新能源自驾情侣/家庭 | 多日路线、舒适作息、补能余量、酒店稳定、景点适配 | 地图能算单段路线，但用户仍需手工拼接每天活动和补能 |
| 跨城交通 + 本地游用户 | 比较飞机/高铁/火车，衔接机场/车站、酒店与每日活动 | 班次、景点、餐饮和住宿分散在不同入口 |
| 需要反复修改的深度旅行者 | 地图加点、删除景点、改变停留时间后整体重排 | 局部收藏容易，跨日时间/路线/酒店闭环需要人工重算 |

RoadMan 的核心任务不是“告诉用户哪里好玩”，而是把需求、证据、交通、时间、能耗、住宿、餐饮、风险和修改历史编排成一个可验证的多日执行计划。

## 2. 与公开产品定位的合理比较

比较只依据各产品官方公开页面，不声称竞品“没有”未公开能力。

| 维度 | 高德地图官方公开重点 | 马蜂窝官方公开重点 | RoadMan 当前可验证重点 |
|---|---|---|---|
| 路线与导航 | 实时交通、驾车/公交/步骑行、多途经点、停车与充电信息 | 目的地与产品内容为主 | 调用在线地图执行路线，但额外维护多日时间、住宿、补能和闭环状态 |
| 目的地内容 | 地点搜索、周边生活与商家信息 | 攻略、游记、主题灵感、当地活动和商品 | 多源候选先研究再策展，采用项保留来源、时间与适配理由 |
| 多日路书 | 可分享路线/路书 | 行程灵感与自由行内容 | 把每日三餐、住宿、活动、休息、补能、返程作为统一校验对象 |
| 新能源余量 | 充电设施与路线能力 | 非核心公开定位 | 连续 SOC、实测/功率补能、车辆功率上限、安全余量与异常降级 |
| 修改闭环 | 路线点编辑 | 内容与商品选择 | 自然语言或地图编辑 → 修改预览 → 用户确认 → 路线/时间/SOC/住宿重算 |
| 可追溯性 | 以实时地图服务为核心 | 以内容与交易服务为核心 | 每个 adopted 候选、风险、工具调用和降级状态可追溯 |

官方资料：

- 高德地图产品与路线能力：[高德地图产品页](https://mobile.amap.com/cn/Index.aspx)、[路线规划帮助](https://www.amap.com/ssr/doc/route-plan)、[开放平台路线规划](https://lbs.amap.com/product/path)。
- 马蜂窝目的地、攻略和当地产品：[目的地页](https://m.mafengwo.cn/mdd/)、[马蜂窝首页](https://www.mafengwo.cn/index.php)、[当地玩乐](https://m.mafengwo.cn/localdeals/)。

RoadMan 不取代实时导航，也不试图复制攻略社区。它位于“灵感/内容”和“实时导航”之间，负责把多源信息编排成出发前可执行、可修改、可复核的路书。

## 3. 四个可演示的差异点

### 3.1 多约束路书编排，而非单段路线搜索

```mermaid
flowchart LR
    A[随意自然语言] --> B[地点/日期/同行人/舒适度]
    B --> C[目的地研究与代表性候选]
    C --> D[每日地理主轴]
    D --> E[路线 + 三餐 + 酒店 + 活动]
    E --> F[补能 + 休息 + 天气 + 预约]
    F --> G[每日复核与自动修复]
    G --> H[可执行路书]
```

著名景点不是靠维护“南京清单”“成都清单”硬编码，而是先根据目的地范围检索公开来源；同一句话里的省份与明确子城市会先裁决出真正路线锚点，同一景区的入口/停车场等 provider 变体会合并。研究/策展智能体给出证据和适配评分后，路线层再结合相邻转场距离选择，只有路线实际经过的候选才进入当天活动卡。

### 3.2 新能源补能余量可解释

路线阶段显示起始 SOC、预测消耗、补能前 SOC、补能量、功率、时长、补能后 SOC 和到达 SOC。真实补能量优先，缺失才估算；估算位置不冒充真实可用桩。车辆具体版本先查主目录，缺失时动态查询多个公开车型数据源，所有参数保留来源和缺失/估算标记，避免用单一硬编码车型支撑续航差异化。

### 3.3 多智能体 + 确定性校验分工

模型擅长理解“情侣舒适为主”“不要每天换酒店”“三天都待在九宫山”等语义；路线工具和校验器负责坐标、时间、连续性、能量和闭环。这样既保留 Agent 的灵活性，也避免把安全判断交给一段自由文本。

### 3.4 修改不是聊天建议，而是真实状态变更

用户删除的地点进入排除集合，重排时不会被智能体重新加回；地图选点或自然语言修改先生成 PlanPatch 预览，只有用户确认才写入 canonical Trip。完成一批编辑后统一重算路线、时间、住宿锚点与能耗，并再次校验；每天重新闭合到酒店，返程班次时间紧时先舍弃可选景点，同地锚点不会生成一张零距离“移动”卡。

## 4. 用户价值量化框架

复赛阶段不应虚构节省金额或商业收入。建议用可采集指标证明价值：

| 价值 | 指标 | 采集方式 |
|---|---|---|
| 降低规划时间 | 从输入到首个可执行方案的分钟数 | Job 开始/完成时间 |
| 降低手工拼接 | 用户需要跳转外部应用的次数 | 可用性测试观察 |
| 提高计划完整性 | 三餐、住宿、返程、休息、补能覆盖率 | 校验器结构化结果 |
| 提高修改成功率 | 修改预览确认后一次重排通过率 | PlanPatch 与 verification 日志 |
| 提高安全透明度 | 估算/未知字段被正确标记比例 | warning 与 source 审计 |
| 控制推理成本 | 单条完整行程 Token、工具次数、P95 时延 | `/api/v1/ops/metrics` |

建议复赛前邀请 8–12 名目标用户，分别用传统“地图 + 攻略 + 备忘录”流程和 RoadMan 完成同一任务，比较时间、遗漏项、修改次数和主观信心。样本较小时只报告描述性统计，不做夸大的显著性结论。

## 5. 商业路径

### 5.1 B2C：高级路书与家庭车辆档案

- 免费层：基础多日规划、地图浏览、单次导出。
- 订阅层：多车辆档案、进阶能耗模型、历史版本、协作编辑、出发前风险复核。
- 边界：不以付费改变安全校验结论，不通过出售精确轨迹获利。

### 5.2 B2B2C：车企、租车与营地/目的地服务

- 向车企 App 或租车服务提供“车型参数 + 多日路书 + 补能余量”的白标能力。
- 向精品民宿、营地和目的地机构提供可审计的候选接入，但商业候选必须标记赞助关系，不能混入自然排序。
- 以 API/SDK 输出结构化计划，不接入车辆控制，不承担自动驾驶决策。

### 5.3 企业差旅与团建

把多人偏好、固定参观点、班次、酒店和时间窗作为约束，输出可确认的路线与风险清单。该方向需要新增组织权限、审批、发票/预算和多租户隔离后才能商业上线。

## 6. 商业闭环与护城河

```mermaid
flowchart LR
    U[用户真实需求] --> P[结构化约束与修改]
    P --> E[可追溯计划]
    E --> F[校验与用户反馈]
    F --> M[匿名化评测指标]
    M --> C[能耗/排序/修复策略改进]
    C --> E
```

护城河不是某一个模型调用，而是以下组合：

- 跨需求、地点、路线、时间、能量和住宿的统一领域模型；
- 失败可解释的 verify → repair 数据；
- 车型与真实路况条件下的误差校准集；
- 用户确认过的修改意图与计划版本；
- 多 provider 可替换的 Skill 契约和降级策略。

数据飞轮必须以用户授权、最小化收集和可删除为前提。当前 Demo 不具备账号级长期画像，不能把设想写成现有能力。

## 7. 复赛表达建议

一句话定位：

> RoadMan 不是另一个地图或攻略社区，而是把目的地证据、跨城交通、每日路书、车辆续航和用户修改编排成可验证闭环的多智能体旅行工作台。

三分钟商业价值段落建议：

1. 先展示一个“地图能导航，但不能替用户维护完整多日计划”的真实任务。
2. 展示连续 SOC、同酒店策略、三餐/休息和修改重排。
3. 用评测看板证明结果不是只靠画面。
4. 最后说明 B2C 订阅与车企/租车白标两条路径，以及不接车辆控制的责任边界。
