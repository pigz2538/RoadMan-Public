# Data Sources & Compliance

**🌐 Language / 语言：** **English** | [**中文**](数据来源与合规说明.md)

> Corresponds to competition material "4. Data Sources & Compliance". This document describes the **data types** RoadMan handles, **data sources, authorization status, anonymization, privacy protection, industry risk notices**, and the boundary that RoadMan **does not replace professional decision-making**. RoadMan is currently a locally controlled competition demo, not a public multi-user service; the relevant boundaries are stated honestly in "Current Boundaries & Future Upgrades" at the end.

---

## 1. Data Types

| Type | Content | Handling |
| --- | --- | --- |
| User input | Travel requirements (natural-language text), attachments (images/PDF/DOCX/Markdown/XLSX), edit instructions, map point picks | Used for requirement extraction, semantic edits and context; stored in Trip / version / message state |
| Vehicle parameters | Vehicle catalog identity info (brand/series/model), range & battery capacity, seat count | Saved after user confirmation; only used as planning context; license plates are never collected |
| Conversation & edit state | Clarification Q&A, semantic edit messages, patch preview/confirm/rollback | Stored in `Trip`, `PlanPatch`, `TripVersion` for restore and rollback |
| External call results | Geocoding / POI / routes / weather / schedules / hotels / restaurants / attractions / source links / risks | Normalized into domain objects with `SourceRecord` (source, URL, fetch time, status) |
| Attachment uploads | Documents and images provided by the user | Stored in `UPLOAD_DIR`; the database only keeps safe filenames and metadata; extension/MIME whitelist validation |

**Not collected by default**: ID numbers, license plates, payment info, precise home addresses, continuous location traces. Such information in prompts or attachments is never treated as mandatory fields.

## 2. Data Sources & Authorization Status

| Data/Capability | Source | Purpose | Authorization & Notes |
| --- | --- | --- | --- |
| AMap WebService | [https://lbs.amap.com](https://lbs.amap.com/) | Geocoding, real driving/walking/cycling/transit routes, traffic, POI | Requires `AMAP_WEBSERVICE_KEY`; subject to AMap Open Platform developer terms, quotas, map-display and caching rules |
| AMap JSAPI (browser map) | AMap JSAPI v2 | Map rendering, point picking, route display | Requires `VITE_AMAP_JSAPI_KEY` + `VITE_AMAP_SECURITY_JS_CODE`; configure domain whitelist per the platform; falls back to `MockRouteMap` without keys |
| Open-Meteo | [https://open-meteo.com](https://open-meteo.com/en/docs) | Trip-date weather, precipitation probability, elevation reference | No key by default; **free for non-commercial use**; commercial use requires an `apikey` (`customer-` prefix); data from multiple national weather services — attribution per source and license requirements |
| OpenTripMap | [https://opentripmap.io](https://opentripmap.io/) | International & open attraction candidates | Requires `OPENTRIPMAP_API_KEY`; data based on OpenStreetMap (ODbL) and Wikidata/Wikipedia — **source & attribution must be retained**, terms of service apply |
| FlyAI / Fliggy CLI | Fliggy open capabilities (`@fly-ai/flyai-cli@1.0.16`) | Train/flight/ferry schedules, hotels, dining, POI and semantic search | Requires `FLYAI_API_KEY`; a commercial travel information service — call scope, display, caching and re-licensing per its commercial terms; without a key or CLI returns `SKILL_NOT_CONFIGURED`; with or without results, the response is always truthful |
| Vehicle catalog service | [https://tool.bitefu.net/car](https://tool.bitefu.net/car/) | Brand/series/model catalog identity | Public endpoint, no key; only catalog identity is imported; range/energy are confirmed by the user or estimated from context |
| DeepSeek official Chat Completions | [https://api-docs.deepseek.com](https://api-docs.deepseek.com/api/create-chat-completion/) | Requirement understanding, destination research, candidate curation/ranking/fitness, semantic edits, attachment understanding | Requires `DEEPSEEK_API_KEY`; OpenAI-compatible protocol. The model's private chain-of-thought comes back via `reasoning_content`; **RoadMan does not store it or write it to logs/SSE/exports**; usage/log retention per DeepSeek's data-processing terms |
| Web research (public pages) | Zhihu, Sohu, 163, Bendibao, Klook, etc. (retrieved by the destination-research agent) | Attraction/food/district/special-event candidates & summaries | Only source links and public summaries are kept as candidate evidence; **images without a clear re-usable license are not packaged into public exports** |
| Browser geolocation | User's explicit browser grant | Local weather on the home page | Used locally in the browser only; falls back to a default location when denied; **precise GPS is not stored long-term** |

**Source recording & degradation**: all external data keeps its source, fetch time and status via `SourceRecord`; estimates are explicitly marked (e.g. `ENERGY_STOP_ESTIMATED`, `CHARGING_POWER_ESTIMATED`, `WEATHER_DATA_DEGRADED`) and never treated as live facts. Missing schedule/opening/ticketing/reservation fields stay `unknown` / `unavailable` — no fabricated IDs, prices or opening statuses are generated.

> About `SourceRecord.license`: currently only the Open-Meteo source fills in a license field (recorded in the project as `CC BY 4.0`). Before submission, a provider config table should be created to fill in the license/terms version, fetch time, cache period and exportability for every source, and to confirm third-party redistribution & attribution requirements item by item.

## 3. Anonymization

- **Credentials**: API keys are only injected via the untracked `.env` or system environment variables — never into git, SSE, logs, exports or frontend runtime logs. `deploy/scripts/sync-local-secrets.ps1` syncs from local `Skills/*/apikey.txt` to the ignored `.env`, omitting values in output.
- **Logs & audit**: call audits only store adapter/provider, success status, latency, cache, error code and source summary — **no keys, cookies, headers or sensitive request-body fields**.
- **Model output**: the model's private chain-of-thought (`reasoning_content`) is never persisted or logged; SSE only pushes displayable stage progress and structured decisions, never internal prompts or raw model output.
- **Attachments**: the database only keeps safe filenames and metadata; upload content lives in `UPLOAD_DIR`; filenames pass whitelist validation.
- **Demo evidence**: screenshots, videos and runtime evidence must be anonymized before submission — hide keys, personal paths and precise locations.

---

## 4. Privacy Protection

- **Current form**: locally controlled competition demo, single-user by default; **no account system, no cross-trip location memory, no long-term user profiling**.
- **Attachment retention**: 30 days by default, adjustable via `FILE_RETENTION_DAYS`; scheduled tasks only delete files inside the `UPLOAD_DIR` security boundary.
- **Deletion & cascade**: when a user deletes a trip, the backend cleans up the trip document, message/planning state, saved versions, associated attachment metadata, background tasks and this trip's Skill call records in one data operation, and deletes the attachment entity files inside the safe directory — an unrecoverable hard delete; the frontend requires a second confirmation before executing.
- **System health audits**: health audits not tied to a specific trip are not deleted with a single trip.
- **Local boundary**: local development defaults to SQLite (`DATABASE_URL=sqlite+aiosqlite:///./roadman.db`); production/Compose uses PostgreSQL. In both modes, uploads and credentials never enter the repository.

## 5. Industry Risk Notices

Routes, weather, opening hours, tickets, schedules, traffic and prices may change. RoadMan records sources, times and degradation status, but exported results **cannot replace** real-time information from scenic areas, transport operators, road authorities or vehicle manufacturers. Re-check before departure:

- Reservation & real-name/time-slot entry rules, tickets and price ranges;
- Road closures, **severe weather** (marked with risk codes such as `HEAVY_PRECIPITATION`, `EXTREME_TEMPERATURE`, `HIGH_WIND`, `LOW_VISIBILITY`);
- Charging availability (marked with `ENERGY_STOP_SCHEDULED`, `ENERGY_STOP_UNAVAILABLE`, `CHARGING_POWER_ESTIMATED` — estimated charging stops are **points to be confirmed**, never presented as operating charging/gas stations);
- Transport schedules and cross-city timetables;
- Continuous-driving rest and night driving (marked with `REST_STOP_SCHEDULED`, `CROSS_DAY_ARRIVAL_REST`, `NIGHT_DRIVING`; long trips are split by the daily cap with overnight stays reserved).

**Estimates are never disguised as facts**: when real road geometry is unavailable, straight lines are not presented as navigation routes; estimated charging stops, simulated range samples and illustrative basemaps are all explicitly labeled, never presented as live real data.

---

## 6. Boundary: Not a Substitute for Professional Decisions

RoadMan is a **planning aid for the pre-departure and trip-adjustment phase**, with explicit boundaries:

- **No CAN-bus, vehicle control, autonomous-driving or driver-assist execution interfaces**; it does not control steering, braking, powertrain, charging or doors.
- **No autonomous-driving decisions**; it does not replace real-time navigation, road & weather authority bulletins, transport & scenic-area operator information, vehicle instruments or driver judgment.
- Planning results and exported files **must not be used as** autonomous-driving instructions, emergency-response conclusions or vehicle-performance promises.
- Real navigation, road bulletins, vehicle state, charging-facility availability and driver judgment always take final priority.
- Model output must pass structured Schema, coordinate/route tooling and deterministic validation; **the model cannot override hard route, time, energy, closure and vehicle-safety conclusions** (`verify_plan` blocking items take priority over model suggestions; fixable issues go through up to 4 automatic repair rounds; only when hard constraints are still violated is the user asked to adjust).

## 7. Current Boundaries & Future Upgrades

| Scope | Current (local / controlled demo) | Required before upgrading to a public multi-user service |
| --- | --- | --- |
| Accounts & auth | No account system, single controlled user | Login, resource-level auth, tenant isolation, stricter rate limiting |
| Data-subject rights | Cascade hard delete per trip | Privacy notice, data export, consent withdrawal, data-subject request process |
| Location/order/vehicle data | Real orders, location traces and vehicle data not collected by default | Full privacy notice, access control, retention periods and deletion mechanisms |
| Service commitment | No SLA | Circuit breakers, alerting, capacity testing, disaster recovery |
| Third-party authorization | Per-source disclosure of source & calls | Add third-party license/terms versions, cache/re-licensing and export-reuse boundaries |

> The authorization status listed in this document reflects public documentation and repository implementation at the time of writing; the actual status follows each provider's latest terms and the `/api/v1/skills/health` response. RoadMan's local credentials (`.env`, `Skills/*/apikey.txt`) are never synced to the repository.
