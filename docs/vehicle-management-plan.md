# RoadMan 车型管理与车辆能力接入实施计划

> 状态：待实施方案（2026-08-03）
> 关联规范：`Skills/carinfo/SKILL.md`、`RoadMan_分阶段实施总规划.md`、`docs/domain-model.md`

## 1. 目标与边界

车型管理不只是一个“换车弹窗”，而是把车辆能力变成行程规划的可验证约束。用户可以搜索、确认、编辑和切换车辆；规划 Agent 必须读取已确认的车辆能力，给出续航、补能、座位、路况和驾驶强度相关的安排，并在数据不完整时明确说明来源和不确定性。

本计划覆盖：

- 车型搜索、车型/配置确认、当前车辆、收藏车辆和手动修正；
- 车辆能力标准化、来源追踪、缓存和过期策略；
- 与路线、补能、天气、驾驶休息和公共交通降级策略的接口；
- 前端车型管理页面、规划前确认摘要和异常提示；
- 单元、接口、端到端和离线数据测试。

不在第一期范围内：真实下单、保险报价、金融方案、车辆远程控制和需要用户账号授权的厂商接口。

## 2. 现状与主要缺口

当前首页已经有车型入口，规划也会显示默认纯电 SUV，但车辆能力仍偏向演示数据，缺少稳定的用户选择和可追溯的配置快照。`Skills/carinfo` 提供了四级查询链路的规范，后端需要把它落成可测试的适配器，而不是在页面或规划器中写死车型字段。

主要缺口：

1. 没有统一的车型身份（品牌/车系/年款/配置）和能力模型，容易把同车系不同续航版本混用。
2. 没有“搜索结果 → 配置确认 → 能力快照”的状态机，来源、更新时间和置信度无法展示。
3. 规划器没有强制使用车辆约束，补能站、休息段、剩余电量和不可行路线的降级策略不完整。
4. 用户无法修正实际续航、当前电量、充电习惯、油价/电价或是否允许跨城补能。
5. 缓存、限流、失败重试和 API Key 隔离尚未形成统一约定。

## 3. 领域模型

建议在 `backend/app/domain` 建立以下实体（字段使用 SI/公制单位，展示层再本地化）：

### 3.1 VehicleProfile

```text
id / user_id / is_current / is_favorite
brand / series / model / year / trim / source_vehicle_id
power_type: petrol | diesel | hybrid | phev | ev | other
seats / curb_weight_kg / cargo_litre
range_km (标准工况) / usable_battery_kwh / fuel_tank_l
consumption_kwh_per_100km / fuel_l_per_100km
charging_ports[] / max_dc_kw / max_ac_kw / charge_time_10_80_min
source_snapshot_id / confidence / updated_at
```

### 3.2 VehiclePreference

保存用户对真实车辆的修正，不覆盖原始来源：当前电量、出发电量、最低安全余量、实际综合能耗、单次最长驾驶时长、休息间隔、是否允许慢充/快充、是否允许公共交通替代、是否携带儿童或大件行李等。

### 3.3 VehicleSourceSnapshot

保存来源名称、来源链接、抓取时间、原始字段哈希、解析版本、字段级置信度和错误信息。任何规划结果引用车辆能力时，都应能回溯到快照；过期数据只能作为估算并标注“需要确认”。

### 3.4 VehicleCapability

给规划器使用的只读投影，包含 `usable_range_km`、`safe_range_km`、`energy_per_km`、`max_drive_minutes`、`recommended_break_minutes`、`can_use_fast_charge` 等已经过单位换算和用户修正的字段。规划器不直接读取网页原始响应。

## 4. carinfo 接入链路

严格按 `Skills/carinfo/SKILL.md` 的四级链路实现：

1. **意图解析**：Agent 将“我的车”“换成 Model Y”“纯电 SUV”等自然语言转为候选条件，并保留原始语义；不使用前端字符串替换作为最终判断。
2. **身份解析**：品牌 → 车系 → 年款 → 配置逐级确认。多个候选时返回候选列表，不猜测具体续航版本。
3. **配置查询**：按来源优先级获取规格、能源参数、充电参数、座位和尺寸；对缺失字段保留 `null`，禁止用另一个版本的数据填充。
4. **标准化与校验**：统一单位、校验范围、去重和来源时间；不合理值进入 `needs_confirmation`，不能直接驱动路线规划。
5. **快照与缓存**：按 `source_vehicle_id + parser_version` 缓存；短期缓存减少重复请求，长时间未更新时显示过期提示。
6. **用户确认**：在规划开始前展示“车型、续航、电量、最低余量、数据来源”，用户确认后才写入当前车辆。

Agent 负责理解和选择候选，确定性代码负责单位换算、冲突校验、缓存和权限。这样既保留 Agent 的语义能力，又避免把错误的车型参数带进路线计算。

## 5. 后端 API 设计

建议在 `/api/vehicles` 下提供以下接口，响应统一使用 `shared` 的 Pydantic/TypeScript schema：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/vehicles/search?q=&power_type=&page=` | 搜索品牌/车系/配置候选 |
| `GET` | `/api/vehicles/{id}` | 返回规范化详情和来源快照 |
| `POST` | `/api/vehicles/resolve` | 由 Agent 的候选条件解析具体配置 |
| `GET` | `/api/vehicles/current` | 当前车辆及用户修正后的能力 |
| `PUT` | `/api/vehicles/current` | 选择车辆或保存用户修正 |
| `POST` | `/api/vehicles/{id}/refresh` | 手动刷新来源数据 |
| `GET` | `/api/vehicles/sources/status` | 查看来源可用性、缓存和错误 |
| `DELETE` | `/api/vehicles/{id}` | 删除收藏/历史车辆（当前车辆需先切换） |

错误响应应区分：候选过多、来源暂时不可用、字段缺失、配置冲突、用户输入越界。所有外部 Key 只从环境变量或本地忽略文件读取，接口日志不得打印 Key 和完整原始响应。

## 6. 前端车型管理设计

车型管理弹窗建议分成四个区域：

- **当前车辆摘要**：车型、动力类型、可用续航/油量、当前电量、最低余量和数据更新时间；
- **搜索与候选**：搜索框、动力筛选、品牌/车系级联、配置差异对比；候选卡明确“官方/第三方/用户修正”来源；
- **能力修正**：电量、真实续航、能耗、充电功率、连续驾驶上限和休息偏好；修正字段显示为用户值，不覆盖来源值；
- **确认操作**：保存为当前车辆、收藏、刷新数据、取消。保存后给出影响范围，提示是否重新规划当前行程。

规划页的车辆信息只显示最终能力摘要，点击可回到车型管理。加载、无结果、来源失败和过期状态都要有明确的中文提示；不能把内部字段名、Agent 原始 JSON 或异常堆栈展示给用户。

## 7. 规划与多 Agent 协作

车型能力进入 `PlanningContext` 后，由以下协作步骤消费：

1. **Vehicle Agent** 输出能力投影和约束解释；
2. **Route Agent** 计算驾车/公共交通/步行/骑行候选路线；
3. **Energy Agent** 按安全余量插入充电/加油/休息段，比较站点绕行成本和营业时间；
4. **Schedule Agent** 将驾驶上限、三餐、住宿、景点停留和天气窗口放入日程；
5. **Review Agent** 检查闭环、跨天时间、连续驾驶、能量余量、站点可达性和数据来源；
6. **Conversation Agent** 向用户解释假设，并支持“换车、少开一点、允许慢充”等自然语言修改。

任一 Agent 失败都返回结构化的 `reason_code`、`user_message`、`fallback_options`，不能只显示“规划失败”。当驾车不可行时，按用户偏好尝试公共交通、步行或骑行，并把换乘和步行段作为正式阶段卡片。

## 8. 安全、性能与可观测性

- Key 仅存在于环境变量/本地忽略文件，新增 `.gitignore` 规则覆盖 `Skills/**/apikey.txt`、`secretkey.txt`、`apipkey.txt`；
- 外部请求统一超时、限流、指数退避和熔断；缓存命中时不重复请求；
- 每次规划记录 `vehicle_profile_id`、`source_snapshot_id`、能力摘要哈希和规划版本，便于复现；
- 指标包括来源成功率、解析冲突率、缓存命中率、规划因车辆约束失败的比例和用户修改后重规划耗时；
- 车型数据按用户隔离，删除车辆时同时清理用户修正和缓存关联，不删除共享的匿名来源快照。

## 9. 分阶段实施与验收

### M1：模型与契约

完成领域模型、共享 schema、迁移、错误码和离线 fixture。验收：同车系不同配置不会串数据，单位和空值校验通过。

### M2：carinfo 适配器

完成搜索、身份解析、详情、快照、缓存和来源状态；加入超时/重试和脱敏日志。验收：无 Key 时有可读错误，有 Key 时能生成可追溯快照。

### M3：车型管理 UI

完成当前车、候选对比、用户修正、收藏和删除；加入响应式布局和无障碍键盘操作。验收：刷新页面后当前车保持，切换车辆可触发重规划提示。

### M4：规划约束接入

完成续航/油量、连续驾驶、休息、补能和交通方式降级；Review Agent 输出检查项。验收：长途纯电路线自动分段，异常需求可解释并给出替代方案。

### M5：质量与发布

补齐 API、组件、端到端、离线和故障注入测试；更新 README、`project.md` 和部署变量。验收：没有内部字段泄漏，敏感文件不进入 Git，`git diff --check`、后端测试和前端构建通过。

## 10. 需要用户确认的产品决策

1. 是否允许把用户手动修正的续航作为默认规划值，还是每次仅作为本次行程覆盖值；
2. 车型来源优先级（厂商/官方公告/第三方数据库）及价格信息是否只展示链接不做承诺；
3. 是否默认允许公共交通替代驾车，以及切换时是否需要再次确认；
4. 当前车辆删除后，历史行程是否保留当时的能力快照；
5. 是否在本地保存完整车型来源响应，还是只保存规范化字段和哈希。
